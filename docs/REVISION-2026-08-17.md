## 🔴 1. El drenaje de la cola marca los dos canales como enviados

**`worker/app.js:549-552`**

```js
if (result.created && input.notified) {
  await env.DB.prepare("UPDATE lead_notifications SET status='sent',attempts=1,sent_at=?,updated_at=? WHERE lead_id=?")
```

`input.notified` es un booleano **OR** de los dos canales (`app.js:251-254`: el bucle pone
`notified = true` si *alguno* entrega) y el `UPDATE` **no filtra por `channel`**.

**Escenario.** Telegram configurado, WhatsApp no (que es el estado actual, ver hallazgo 2).
Cae D1 un rato. Llega un lead → Telegram sale bien → `notified = true` → se encola en KV.
Vuelve D1, el cron reinserta y pone **las dos filas** (`telegram` y `whatsapp`) en
`status='sent', attempts=1, sent_at=<ahora>`. El aviso de WhatsApp nunca se envió, ya no
entra en el `WHERE` de `processNotifications` y **no se reintentará jamás**. El panel muestra
"whatsapp: sent". Es una mentira registrada en base de datos, que es la peor clase de bug de
notificaciones: no se nota.

**Parche.** Guardar qué canales entregaron, no un booleano:

```js
// app.js — en el catch de storeLead
const notifiedChannels = [];
for (const channel of ['telegram', 'whatsapp']) {
  try { if ((await deliver(env, channel, notificationText(inputToNotifiable(input)))).ok) notifiedChannels.push(channel); } catch (_) {}
}
const notified = notifiedChannels.length > 0;
// …
await env.KV.put(`leadq:${input.requestId}`, JSON.stringify({ ...input, notified, notifiedChannels }), { expirationTtl: 30 * 86400 });
```

```js
// app.js — en drainQueuedLeads
const channels = Array.isArray(input.notifiedChannels) ? input.notifiedChannels
  : (input.notified ? ['telegram', 'whatsapp'] : []);   // compat con lo ya encolado
if (result.created && channels.length) {
  const now = new Date().toISOString();
  await env.DB.batch(channels.map((ch) => env.DB
    .prepare("UPDATE lead_notifications SET status='sent',attempts=1,sent_at=?,updated_at=? WHERE lead_id=? AND channel=?")
    .bind(now, now, result.id, ch)));
}
```

## 🔴 2. Inanición del cron por filas `skipped` perpetuas — activo hoy

**`worker/app.js:562`** (query del cron), **`:214`** y **`:222-224`** (estado `skipped`)

Una fila `skipped` (canal sin configurar) **no consume intentos** y se reprograma a `+6 h`
**para siempre**, hasta que el lead caduque a los 24 meses. El `SELECT` del cron las vuelve a
incluir siempre (`OR status = 'skipped'`), no tiene **`ORDER BY`** y va con `LIMIT 25`.

Esto no es hipotético: `docs/OPERATIONS.md` dice que `TEAM_WHATSAPP` y `TWILIO_FROM` siguen
pendientes, así que **cada lead que entra deja una fila `whatsapp: skipped` inmortal**.

**La aritmética.** Cada lead con un canal sin configurar exige 4 procesados/día (24 h ÷ 6 h).
La capacidad del cron es 288 ticks/día × 25 = 7.200 procesados/día. A partir de **~1.800
leads** la ventana se satura de forma permanente. Y como no hay `ORDER BY`, SQLite devuelve
el orden del plan de ejecución (típicamente rowid = los más antiguos primero): cuando se
sature, los `pending`/`failed` de los **leads nuevos** quedan al final y no se reintentan
nunca por cron.

**Segundo problema en la misma función.** 25 leads × 2 canales × 8 s de timeout = hasta
**400 s** de trabajo secuencial en un cron que dispara cada **300 s**, sin ningún lock. Dos
invocaciones solapadas seleccionan los mismos `lead_id` y ambas llaman a `deliver` →
**avisos duplicados al equipo**.

**Parche.** Tres cosas: priorizar, ordenar, y no revisitar canales que siguen sin configurar.

```js
// app.js — processNotifications: si el canal sigue sin configurar, no gastes el tick
for (const job of jobs) {
  if (!force && job.next_attempt_at && job.next_attempt_at > new Date().toISOString()) continue;
  // …
}
```

```js
// app.js — scheduled: dos consultas, prioridad a lo entregable, y ORDER BY explícito
const due = (await env.DB.prepare(`
  SELECT lead_id FROM lead_notifications
  WHERE status IN ('pending','failed') AND attempts < 5
    AND (next_attempt_at IS NULL OR next_attempt_at <= ?)
  GROUP BY lead_id ORDER BY MIN(updated_at) ASC LIMIT 20`).bind(now).all()).results;
const idle = (await env.DB.prepare(`
  SELECT lead_id FROM lead_notifications
  WHERE status = 'skipped' AND (next_attempt_at IS NULL OR next_attempt_at <= ?)
  GROUP BY lead_id ORDER BY MIN(updated_at) ASC LIMIT 5`).bind(now).all()).results;
for (const row of [...due, ...idle]) await processNotifications(env, row.lead_id);
```

Y el `DELETE FROM leads WHERE expires_at <= ?` (`:564`) conviene acotarlo con
`LIMIT 500` (D1 tiene límites de tiempo y tamaño por sentencia; una purga acumulada puede
chocar con ellos y abortar el tick entero).

> **Atajo que resuelve el 90%:** configurar `TEAM_WHATSAPP` y `TWILIO_FROM` de una vez.
> Con los dos canales configurados, `skipped` deja de existir. Sigue mereciendo la pena el
> parche, porque el diseño no debería depender de que nunca falte configuración.

## 🔴 4. `loadTurnstile()` cachea la promesa rechazada

**`assets/funnel.js:82-94`**

```js
if (turnstileLoader) return turnstileLoader;      // ← línea 84
// …
script.onerror = function () { reject(new Error('turnstile_load_failed')); };   // ← nunca limpia turnstileLoader
```

Si `challenges.cloudflare.com/turnstile/v0/api.js` falla **una** vez —4G inestable, proxy
corporativo, extensión de bloqueo, un DNS que parpadea— `turnstileLoader` queda siendo una
promesa rechazada para el resto de la carga de página. Todas las llamadas posteriores a
`VELAI_HUMAN.execute()` devuelven el mismo `turnstile_load_failed` sin reintentar siquiera la
inserción del `<script>`. Afecta al chat, al formulario de demo y a los dos quizzes.

**Escenario.** Un usuario en el metro abre el chat en `/restaurantes/`, manda "hola", el
script no carga, ve *"Ups, ahora mismo no puedo responder…"*. Recupera cobertura y reintenta
tres veces: el mismo error, siempre. Solo se arregla navegando a otra página o recargando —
y el copy del chat ni siquiera se lo sugiere (el del leadform sí).

**Parche** (dos líneas):

```js
turnstileLoader = new Promise(function (resolve, reject) {
  var script = document.createElement('script');
  script.src = 'https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit';
  script.async = true; script.defer = true;
  script.onload = resolve;
  script.onerror = function () {
    turnstileLoader = null;              // ← permitir reintento
    script.remove();
    reject(new Error('turnstile_load_failed'));
  };
  document.head.appendChild(script);
});
```

Y en `vai-widget.js`, diferenciar el mensaje cuando el fallo es de verificación humana, para
que el usuario sepa que recargar sirve.

**`assets/funnel.js:112`** — `if (turnstileWidget != null) window.turnstile.remove(turnstileWidget);`

## 🟠 8. `extractPhone` acepta fechas, importes y CIFs

**`worker/app.js:31-38`** — la regex `\+?\d[\d\s().-]{4,}\d` incluye `.`, `-` y espacios;
`normalizePhone` acepta 6–15 dígitos tras limpiar. Verificado ejecutando el módulo:

| Mensaje del usuario en el chat | "Teléfono" extraído |
|---|---|
| `la cita fue el 13-05-2024 y no vino` | `13052024` |
| `Facturo entre 40.000 - 60.000 al mes` | `4000060000` |
| `mi cif es B-12345678` | `12345678` |
| `somos 120.000 - 150.000 clientes` | `120000150000` |

Son frases naturales en una conversación donde Vai pregunta *explícitamente* por el negocio y
el volumen. Cada una dispara `captureChatLead`: una llamada a Haiku, una fila en `leads` y
**dos notificaciones al equipo** con un número inventado. El test de `worker.test.js:14` solo
cubre el caso con letras intercaladas (`'Tengo 2 locales y 40 mensajes al día'`), que sí falla
la clase de caracteres.

**Parche.** Quitar el punto de la clase, exigir longitud de teléfono real y descartar fechas:

```js
const DATE_RE = /\b\d{1,2}[-/.]\d{1,2}[-/.]\d{2,4}\b/;
function extractPhone(text) {
  const source = String(text || '');
  const candidates = source.match(/\+?\d[\d\s()-]{7,}\d/g) || [];
  for (const candidate of candidates) {
    if (DATE_RE.test(candidate)) continue;
    const digits = candidate.replace(/\D/g, '');
    if (digits.length < 9 || digits.length > 15) continue;   // móvil/fijo real
    const phone = normalizePhone(candidate);
    if (phone) return phone;
  }
  return '';
}
```

Y añadir esos cuatro casos al test — es justo el tipo de regresión que vuelve.

## 🟡 10. `deliver` (whatsapp) es todo-o-nada

**`worker/app.js:200-205`** — `results.every((r) => r.ok)`.

## 🟡 11–15. Robustez de entrada y de configuración

**11. Cuerpo JSON `null` → 500** (`worker/app.js:61`). Verificado:

```
POST /lead  body: null  → 500 {"ok":false,"error":"server_error"}
POST /chat  body: null  → 500 {"ok":false,"error":"server_error"}
```

`readJson` devuelve lo que dé `JSON.parse` sin comprobar que sea un objeto; `body.requestId`
sobre `null` lanza `TypeError` y cae en el catch genérico. Ensucia los logs con nivel `error`
y convierte entrada inválida en 5xx. Parche: `if (!parsed || typeof parsed !== 'object' ||
Array.isArray(parsed)) throw new HttpError(400, 'invalid_json');`

**12. `?limit=abc` → `NaN`** (`worker/app.js:476`). `Math.min(100, Math.max(1, Number('abc')))`
es `NaN` (verificado). Se bindea `NaN` en `LIMIT ?`: o D1 lo rechaza (500) o lo convierte a
`NULL`, y en SQLite `LIMIT NULL` significa **sin límite**. Parche: `const raw =
Number(url.searchParams.get('limit')); const limit = Number.isFinite(raw) ? Math.min(100,
Math.max(1, raw)) : 50;`

**13. `adminCorsGuard` frágil** (`worker/app.js:438-441`). Hoy funciona porque
`wrangler.toml` define `ADMIN_ORIGIN = "https://admin.hirevai.com"` exacto. Pero si esa
variable falta, o lleva **barra final**, `origin !== env.ADMIN_ORIGIN` es siempre cierto y
**todo PATCH/POST/DELETE devuelve 403**, mientras los GET siguen funcionando: el panel carga
y lista leads, pero cambiar estado, añadir nota, reintentar y borrar fallan con un `alert()`
genérico. Y no salta ninguna alarma porque `adminHost()` (`:435`) hace fallback silencioso a
`'admin.hirevai.com'`. Parche: normalizar con `new URL(env.ADMIN_ORIGIN).origin` y lanzar
`503 admin_misconfigured` si la variable no existe, en vez de degradar en silencio.

> Sobre CSRF: **no es explotable**. Todas las rutas que mutan estado son POST/PATCH/DELETE y
> en un navegador siempre llevan `Origin`; PATCH/DELETE y el POST de notas con
> `Content-Type: application/json` además exigen preflight, que nunca recibe cabeceras CORS.
> Los GET sin `Origin` pasan el guard pero no mutan nada y la respuesta no lleva
> `Access-Control-Allow-Origin`, así que no se puede leer cross-origin. La protección es
> correcta; lo que es frágil es la configuración.

**14. JWT malformado → 500, y amplificación del JWKS** (`worker/app.js:418-419`, `:425-426`).
`atob`/`JSON.parse` sobre datos del atacante sin `try`: una cabecera
`Cf-Access-Jwt-Assertion: a.b.c` produce `InvalidCharacterError` → **500 `server_error`** en
vez de 401. Y con un `kid` desconocido, la línea 426 fuerza `accessKeys(issuer, true)` → un
`fetch` a `cloudflareaccess.com` **por cada petición no autenticada**, machacando además la
caché global del isolate. Parche: envolver el parseo en try/catch → 401, y limitar el refresco
forzado a uno cada N segundos.

> El resto de la verificación del JWT es **correcta** y merece decirse: `alg !== 'RS256'` se
> rechaza antes de verificar (bloquea `alg:none` y la confusión HS256/RS256), `iss` se compara
> contra `env.TEAM_DOMAIN` y no contra el token (sin SSRF en el JWKS), `aud` se comprueba,
> `exp` exige `Number.isFinite` explícito, y la firma se verifica sobre `parts[0].parts[1]`.
> `decodeBase64Url` es correcto para todos los tamaños (verificado por roundtrip de 0 a 39 bytes).

**15. `LEAD_RETENTION_MONTHS=""` → 1 mes** (`worker/app.js:116-121`). `Number('')` es `0`, que
es finito, así que `Math.max(1, 0)` da **1 mes** en vez del default de 24. Verificado:
`''` → `2026-09-17`, `'24'` → `2028-08-17`. El test solo cubre `'banana'` (NaN), que sí cae al
default. Parche: `const months = Number(env.LEAD_RETENTION_MONTHS) || 24;` antes del clamp.
(De paso: `setUTCMonth` desborda el día — 31 de enero + 1 mes = 3 de marzo. Inocuo con 24.)
